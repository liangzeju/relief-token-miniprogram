# 联调顺序与验收标准

## 1. 联调顺序

不要先把所有页面接上 API。按资金风险从高到低，依次打通以下垂直切片：

1. **捐赠到账 → 合规审核 → MON 取得/存入 Monad 确认**
   - 伪造回调、重复回调、金额篡改必须被拒绝。
   - MON 取得或存入交易失败时捐赠保持 `MON_ACQUISITION_FAILED`/`MON_DEPOSIT_FAILED`，不能变成可用余额。
2. **资金用途 → 任务预算 → Escrow 托管**
   - 不匹配用途不能锁定。
   - 重复点击只能产生一个托管交易。
   - 只有链上 `EscrowCreated` 确认后合同才是 `FUNDS_RESERVED`。
3. **交付批次 → 现场验收 → 分批结算**
   - 验收数量不能超过交付数量。
   - 验收人和合同审批人冲突时拒绝。
   - 结算金额由验收结果计算，不由客户端提交最终金额。
4. **组织兑换申请 → MON 锁定 → 人民币兑付 → MON 结算/释放 → 捐赠者查询**
- 组织必须引用已验收结算、有效兑换规则、价格快照和已验证收款账户提交申请；没有银行/支付回执不能结算 MON。
   - 捐赠者可以按 donation ID 查到所有下游实体和每笔交易哈希。
5. **异常和对账**
   - RPC 中断、Relayer 超时、交易重组、支付回调重复、链下链上余额不一致均进入人工复核。

## 2. 必须通过的验收场景

### 资金和合规

- 已确认到账金额与 MON 取得/存入记录、价格快照和数量相符，单位和精度明确。
- KYC/KYB 未通过时不能取得或存入业务 MON。
- 同一支付参考号只能入账一次。
- 资金用途限制能阻止不合规任务/物资/地区分配。
- 冻结资金不能被新合同预留。

### 权限和职责分离

- 每个写接口在服务端验证角色和 scope；改前端按钮不能绕过。
- 上报人不能批准自己的任务。
- 调度员不能审批自己提出的中选方案。
- 合同审批人不能验收同一合同。
- 验收员不能属于供应方机构。
- 财务结算员不能修改验收数量。

### 链上可靠性

- 每个链上动作有唯一业务键和幂等键。
- 广播后重试不会重复存入、锁定、释放或结算。
- receipt 未达到确认数时业务状态仍为 pending。
- 合约 revert、RPC 失败和 nonce 冲突都有可追踪错误记录。
- Indexer 重启或重复消费日志不会产生重复业务流水。
- Reconciler 能发现数据库余额与链上余额差异并冻结相关账户。

### 全链路可追踪

给定一个捐赠 ID，系统应能返回：

```text
donation
  → fund account
  → ledger entries
  → approved task(s)
  → award(s)
  → contract(s)
  → delivery batch(es)
  → acceptance(s)
  → settlement(s)
  → payout reference
  → MON deposit/escrow/release/settlement transactions
```

公开查询只能显示脱敏后的机构/地区/金额摘要和哈希，授权审计人员才能访问原始证据。

## 3. 上线门槛

### Testnet 门槛

- 合约单元测试、模糊测试和权限测试通过。
- 全链路集成测试通过，覆盖成功和失败分支。
- 至少一次密钥轮换、暂停、恢复和 Relayer 灾备演练。
- 至少一次账、链、银行三方对账，差异为零或有已批准解释。

### Mainnet 门槛

- MON 资产托管性质、运营主体、支付和兑付路径通过专业合规审查。
- 合约第三方安全审计完成，严重问题为零。
- 多签/HSM、限额、白名单和紧急暂停已配置。
- 主网只允许已审核的机构和小额灰度资金。
- 灰度期间每日人工核对，连续通过后才扩大额度。
