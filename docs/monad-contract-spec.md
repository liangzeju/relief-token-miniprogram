# Monad 原生 MON 合约规格

更新日期：2026-09-05。本规格以 [当前业务决策 C01-C16](decision-log.md) 和 [修复实施清单](repair-roadmap.md) 为依据。确认规则、源码能力、测试结果和公共链部署是四种不同状态；本文件不将其中任何一种替代另一种。

## 1. 当前范围与历史边界

正式业务全部使用原生 MON，金额计算使用整数 wei，API 金额使用十进制字符串。用户注册并绑定钱包后捐 MON，由平台采购物资、人力和救援服务；不经过人民币到账确认、人民币兑付或所谓 MON 铸造、销毁流程。（C01-C05）

**本轮新增合约工作仅为 [`contracts/ReliefDonationLedger.sol`](../contracts/ReliefDonationLedger.sol) 抽象账本基础及其测试专用具象 harness 范围。** 基类保留未实现的费用校验钩子，没有可直接部署的具象合约字节码。测试 harness 仅用于在本地补齐该钩子并验证基础逻辑，不是正式资金池或费用政策实现。本地测试结果见验收矩阵，不替代公共链验收或费用授权。

本轮没有部署公共测试网合约，没有费用执行器、合同资金托管锁定或救灾付款执行能力；不能因为已有领域模型、HTTP/UI 或本地测试载体而宣称新版资金池闭环完成。

历史文档中的 `depositMon/acquisitionHash` 人民币来源模型、`lockForRedemption/settleRedemption` 兑换接口、人民币支付回执、直接 `release(contractId, batchId, amount)` 和组织无需钱包的假设均已被新决策替代。它们只作为旧设计追溯，不是当前 ABI、部署步骤、费用授权或业务执行指令。已有原型 `ReliefPool.sol` 也不自动成为新版协议。

## 3. 注册授权捐赠基础

### 3.1 Permit 与签名边界

基类使用 EIP-712 域名 `ReliefFunding`、版本 `2`；域绑定实际 chainId 和 verifyingContract，不能跨链或跨合约复用。当前类型的**字段顺序与类型**以源码 `DONATION_PERMIT_TYPEHASH` 为准：

```text
DonationPermit(bytes32 donationId,address donor,uint8 purpose,bytes32 projectId,uint256 amountWei,uint256 gasReservedWei,bytes32 registrationHash,uint256 nonce,uint256 deadline,uint256 authorizationEpoch,bytes32 feePolicyHash,address registrar)
```

| 字段 | 含义及约束 |
|---|---|
| `donationId` | 非零且唯一的捐赠业务 ID |
| `donor` | 注册绑定的原出资钱包，必须等于交易 `msg.sender` |
| `purpose` | 当前编码 0 表示不限类型，1..5 表示限定类型；正式类型映射需与业务目录一致 |
| `projectId` | 零值表示不限定项目，非零值只能分配到匹配项目 |
| `amountWei` | 捐赠总额，必须大于零并严格等于 `msg.value` |
| `gasReservedWei` | 从总额划出的费用预算，不能超过总额；字段存在不等于费用政策已批准 |
| `registrationHash` | 非零私有注册信息承诺；不是姓名、邮箱或身份证的公开明文/简单哈希 |
| `nonce` | 按 donor 记录的一次性授权编号，可由该钱包提前取消 |
| `deadline` | 授权截止时间；`block.timestamp >= deadline` 时拒绝 |
| `authorizationEpoch` | 对应注册授权签发地址的当前授权代次，用于失效旧 permit |
| `feePolicyHash` | 非零费用政策引用，必须再经最终费用钩子校验；仅非零不能构成费用授权 |
| `registrar` | 位于 `feePolicyHash` 之后的签发地址，属于签名结构；必须等于 `donate` 的 registrar 参数，将 permit 与 epoch 绑定到同一确切授权方 |

`donate(permit, registrar, signature)` 验证的是具有 `REGISTRAR_ROLE` 的注册授权签发方签名。源码 `_validSignature` 对 EOA 使用 OpenZeppelin `ECDSA.tryRecoverCalldata`，要求恢复无错误且地址等于指定签发方；对合约签发方使用 `abi.encodeCall(IERC1271.isValidSignature, ...)` 构造 `staticcall`，要求调用成功、返回数据至少 32 字节，且解码后的 `bytes32` 等于 ABI 补齐的 ERC-1271 magic value。此实现避免引入 bundled OpenZeppelin 5.6 `SignatureChecker` 的 Cancun `MCOPY` 依赖，以适配 Paris 编译目标及本地 Ganache；依赖未变更，ECDSA 校验仍使用 OpenZeppelin 实现。这不是采购合同的双方签名，也不是代扣任意用户余额的授权。原出资钱包仍须自行发送金额精确的原生 MON 交易。

合约先要求 `permit.registrar == registrar`，再校验登记角色、签名、该 registrar 的 epoch、donor nonce、donor 与 sender 一致性、金额及有效期，并调用抽象 `_validateDonationFees(permit)`。撤销 registrar 角色会递增其 epoch；以后重新授予角色也不能复活旧代次授权。签名中固定 registrar 也阻止在原 EOA 授权方被撤销后，把原 permit 改交给另一个 ERC-1271 包装合约，以另一个地址的角色或 epoch 继续使用。不能只检查调用参数中的任意 registrar 而遗漏签名结构里的地址。捐赠 ID 和已使用/取消的 nonce 不可重放。直接 `receive/fallback` 转账被拒绝。

### 3.2 身份与管理权限

注册系统在私有层保存捐赠 ID、出资时注册主体、绑定钱包快照与承诺的映射。承诺使用带随机盐的不透明引用，不能以公开个人资料拼接或低熵姓名哈希替代。链上地址和交易仍可关联，不承诺地址匿名。邮箱本地测试状态、钱包所有权和现实身份/KYC 是不同事实。（C05、C12）

基类现有权限为 `REGISTRAR_ROLE`、`TASK_OPERATOR_ROLE`、`ALLOCATOR_ROLE`、`PAUSER_ROLE`，以及采用 `AccessControlDefaultAdminRules` 的默认管理员延迟移交机制。源码构造参数中的管理员移交延迟为 2 天，属于工程配置，不是费用授权。账户管理 Token 不等于这些链上角色。

基类采用暂停和重入保护；退款失败会回滚账务变化。新增注册角色、任务操作或管理员权限均不产生替别人退款、向任意地址付款或报销任意交易的权力。

## 4. 任务分配与 FIFO 的区别

上游任务须经上报、核验、批准后才能进入正式资金分配。基类 `registerTask` 只检查角色、任务 ID、用途、项目、紧急度和目标金额；它不会自行核验灾情，也尚未完成与业务审批状态的正式接入。（C04、C06）

基类登记任务要求用途 1..5、非零项目、紧急度 1..3 和正目标金额。对一笔捐赠执行分配时：

1. 仅考虑活动、未关闭且仍有预算缺口的任务。
2. 先匹配该捐赠的用途与可选项目限制，Gas 预留不参与救灾净额分配。
3. 紧急度数值较高者优先；同级按**最早登记的 task sequence** 优先。
4. 每次只填补真实缺口，未能分配的净额留在该捐赠 `availableWei`。
5. `donate` 自动尝试一次分配；`allocateRemaining` 仅供原出资钱包或 `ALLOCATOR_ROLE` 再次处理该笔余额。

`MAX_ACTIVE_TASKS = 32` 仅限制同时参与扫描的活动窗口，不限制历史任务总数。可暂停旧任务以释放槽位，再登记新任务；历史记录保留，重新激活也不改变原登记 sequence。达到窗口上限时新增激活会拒绝，不能把可复用数组槽位索引当作优先级。历史任务可持续登记，不代表已完成无限规模性能验证；活动上限是工程防护，扩展性与最坏情况 Gas benchmark 仍待完成。

**任务优先级不等于捐款 FIFO 消费。** 本基类的 `_allocate(donationId)` 处理指定单笔捐赠，不执行所有捐赠来源队列的 FIFO 锁款或实际支出。虽然保存 donation sequence 和 `allocationWei[taskId][donationId]`，不能据此宣称 C16 已在新版合约完成。

完整协议须对满足用途、项目、可用余额要求的来源，按进入资金池的确认链上顺序使用；区块、交易与日志位置用于确定性排序及重放。任务预算、合同锁定、逐批实际付款、结余释放均须保留来源及精确金额。既有链下 FIFO 领域实现不替代新版链上实现与真实事件核验。（C16）

## 5. 采购、履约与付款目标协议

本节为待接入新版合约的目标约束，不是 `ReliefDonationLedger` 已有 ABI。

一个已批准任务可以有多个合同、多个供方及多个履约批次。算法提供推荐与理由，人工审批中选，再由平台采购方与供方钱包对**同一个合同版本**执行 EIP-712 签署。域、任务、标的、单价、数量、预算、收款人、条款和验收摘要、期限、nonce、费用政策版本均须一致。价格、数量、收款人或标准变化必须形成新版本并重新审批、双签；历史批次继续引用原版本。（C06）

双签完成不等于已锁款。只有核验合同版本、用途限制、来源和金额一致的链上锁款事实后，才允许进入履约；不得仅凭客户端状态或手工填入的交易回执开放交付。

岗位与批次约束如下：

- 供方只为本机构已锁款合同登记实际交付，附原始说明及附件。
- 原验收岗位独立于供方、合同审批、交付和不相容的财务处理；通过、部分通过、拒收、争议分别记录，不能覆盖旧结论。
- 拒收/争议的验收数量为 0；部分通过满足 `0 < acceptedQuantity < deliveredQuantity`；通过等于交付量。
- 仅冻结争议批次的付款，其他无争议批次可继续。管理员可分派/改派独立复核人，不能代复核；最新分派为当前授权，历史不可覆盖。复核须引用当前分派、原始交付与验收证据，并新增复核说明及附件。
- 财务岗位独立于合同签署、交付、验收和复核参与者。创建应付不是付款，付款只能针对已满足条件的唯一批次应付。（C07-C09）

每批应付以原合同版本单价乘实际验收或有效复核数量，全部使用整数 wei。累计数量和金额不得超过合同义务及锁定预算；不能以合同全额替代部分验收金额。收款人须为已签合同允许的钱包，不接受客户端任意金额或任意收款地址。（C08）

完整链上付款须绑定合同版本、批次、来源贡献、应付业务 ID、证据/PDF manifest 摘要和精确金额；校验真实交易与事件后才标记已付。发送、pending、失败、确认和重组状态分别保留。失败保留应付和锁款；不能通过任意 `release` 绕过验收、争议、岗位或重复付款守卫。

## 6. 余额、任务关闭与退款

基类当前仅有未分配本金退款：

```text
donation.amountWei = donation.gasReservedWei
                   + donation.availableWei
                   + 已分配到任务的该笔金额
                   + donation.refundedWei

totalDonatedWei = totalGasReservedWei + totalAvailableWei
               + totalAllocatedWei + totalRefundedWei

accountedBalanceWei = totalDonatedWei - totalRefundedWei
```

以上是不包含采购支付、任务释放和 Gas 实支的**当前基础账本**关系，不能直接充当未来完整资金池的会计公式。强制转入造成的实际余额差异不是有效注册捐赠，不得伪造 donation lot 来分配或退款。

`refundUnallocated(refundId, donationId, amountWei)` 要求唯一非零退款 ID，由该 donation 原钱包发起，正金额不超过 `availableWei`，仅退到原钱包。它不能退回已分配任务款、锁款、费用预留，也不完成任务关闭。更换账户绑定钱包不能取得旧钱包退款权；管理员不能无原钱包授权接管退款。（C10）

完整任务关闭流程须先停止新增分配，清理未履约合同、已验收应付、付款中状态及争议义务，再按原来源释放剩余本金。结余保留原用途/项目限制，进入原用户可退款或等待重新授权的余额，不自动挪给其他项目。暂停任务只阻止新增分配，不证明义务已清理，也不会在当前基类中释放已分配资金。

## 7. Gas 政策尚未获准执行

C14/C15 已确认方向：资金池承担本平台业务 Gas，用户先垫付、确认后自动报销，并从捐赠中预留。方向确认不等于具体费率、无限报销或任意费用支出授权。

| 未决事项 | 当前约束 |
|---|---|
| Q01：预留/列支上限、追加授权 | 不自行决定固定比例、金额或追加规则；缺少批准政策时不得启用正式扣费入口 |
| Q02：未用 Gas 预留归属 | 保留原来源，不计平台收益、不自动重新调配；基类没有该部分退款路径 |
| Q03：部署与报销执行启动资金及可报销范围 | 未确认资金来源和范围，不部署、不广播、不借用未来捐款 |

`_validateDonationFees` 是未实现的抽象钩子，不提供默认零费用、无限报销或绕过批准政策的实现；这使基类不能单独作为正式池部署。测试专用 concrete harness 补齐钩子只为测试，不构成业务授权，也不得冒充生产实现。

后续受限费用执行器必须与救灾付款权限分离，按已批准预算核验平台业务交易的链、发送方、目标、方法、参数、金额、事件与确认状态，按交易去重。预留不是费用支出，报销转账不能把同一笔 Gas 计费两次；RPC、存储、邮件、运输等费用不是 Gas。实际网络费用公式和配置在部署前独立核验，本文件不猜测费率或报销额度。

## 8. 付款关联证据与版本化 PDF

原始交付、验收、独立复核和最终发放分别是不同事实。说明及附件保存业务版本、提交者、数量、时间、文件字节摘要和授权范围；不覆盖历史。链上保存必要业务 ID、金额及摘要，私有身份与原始材料留在受控私有层。摘要一致和链上支付不能证明照片内容、实物真实性或病毒扫描结果。

C11 的签发条件是批次已有效验收/复核且已链上付款。目标流程为：

1. 付款前冻结实际贡献来源和证据清单，为每用户/项目/批次形成版本化 manifest。
2. 预生成不可变 PDF，包含稳定核验 QR，对实际 PDF 文件字节计算哈希，将其纳入 manifest。
3. 将 manifest 摘要与该批次实际付款关联；尚未付款时预生成文件不是已完成证书，不作为正式凭证开放下载。
4. 核验付款确认后开放对应版本；核验网页关联实际交易、文件哈希、累计救灾贡献和更正状态。贡献计算排除 Gas。
5. 后续退款、改判、更正或重组保留旧版本并说明新状态，不假称已远程收回下载文件。

PDF 不能包含其自身哈希，也不能预写尚不存在的付款交易哈希；这两项通过外部 manifest/核验记录关联，避免循环依赖。二维码不授予私有附件读取权限，演示 PDF 或本地测试材料不得冒充正式履约凭证。（C11）

## 9. 验证与启用边界

本规格依据决策记录、路线图及抽象基类源码。实际编译、本地 EVM 和回执测试结果记录在 [验收矩阵](acceptance-matrix.md)；这些证据**不包含外部安全审计、正式费用政策、公共链部署及全业务验收**，不得由局部测试推断这些条件已满足。

配套的 `backend/funding-receipts.js` 核验 receipt 所属规范链区块及确认数、配置的运行时代码哈希、交易/调用/事件是否精确匹配，并通过私有 registration resolver 关联注册承诺。它把 donation、task、allocation、refund 和任务启停事实规范化到既有资金领域模型；这不增加 FIFO 实际支出或采购付款能力。

`backend/funding-indexer.js` 是只读持久索引基础：固定链、池、部署区块、确认数及运行时代码哈希，逐段扫描已确认区块，以每块哈希、父哈希、规范事件数和事件指纹保存检查点。整段核验完成后先提交资金投影再推进检查点；中断重启可精确重放，重组回退到共同祖先后重放确认分支。未知池事件、扫描中链变化、投影/检查点不一致及无检查点接管既有账本都会停止。

服务只在资金池地址、RPC、运行时代码哈希和部署区块全部显式配置时创建并轮询索引器；只配置池地址保持保存投影只读，任何半配置拒绝启动。公开状态只说明是否追上确认高度；详细状态要求管理员会话且不返回 RPC。完整后端已在本地真实 EVM 验证自动入账、公开汇总和任务暂停，但当前 8787 启动器显式清除这些配置，且没有公共 Monad 部署、生产 RPC 运行、告警和多实例协调验收。双端页面读取的是已核验保存投影，不是浏览器提供的资金事实。

私有 resolver 现要求匹配原捐赠准备快照的链、资金池及完整 12 字段 permit，不能仅以当前钱包和用户 ID 认领交易；calldata 也须满足规范 ABI 编码。`donation-intent-store.js` 与账户准备适配器保存原注册资料及加盐承诺，禁止覆盖历史，费用策略缺失时关闭准备。准备快照不是已签发授权或入账事实；详情和剩余接入工作见 [捐赠意向说明](donation-intents.md)。

后续验收至少覆盖：

- permit 域/确切 registrar 地址/角色/签名/epoch/nonce/截止/sender/精确 value，EOA 撤权后的 ERC-1271 包装替换拒绝、重复登记、未授权退款、暂停和失败回滚。
- 用途/项目不越界、紧急度与登记顺序稳定、槽位复用、窗口满额、长期历史增长及最坏情况 Gas 基准。
- FIFO 来源锁定与逐批真实支出、同版本双签、岗位分离、批次争议/改派、重复或失败付款、义务关闭与原来源退款。
- 已批准费用政策、预算不足、受限报销、重组与资金对账，以及付款 manifest、PDF 字节、QR 权限和版本更正。
- 手机 H5 与 MetaMask App 的真实交互；微信内引导外部打开，不以桌面缩窄截图代替真机验收。（C13）

只有政策、资金来源、合约实现及相应关卡具备证据后，才讨论部署和正式资金入口。部署前通过 [Monad 官方测试网文档](https://docs.monad.xyz/developer-essentials/testnet) 核对网络参数、RPC、浏览器与费用规则；本规格不复制未经本轮核验的链 ID、地址或实时网络事实，也不宣称已部署。
